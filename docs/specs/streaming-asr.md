# 邊講邊出字

使用者錄音時，每次停頓後，剛說完的句子會經 Codex 辨識。符合下節「逐句打字」條件時，句子辨識好就打進錄音開始時游標所在的欄位；不符合時，句子先顯示在浮條，停止錄音後才把全文送出一次。這裡的「一句」指兩個切點之間的語音，語意上可能還沒說完。

## 逐句打字

錄音開始時，Rust 依游標所在的程式套用「依程式設定」，以下條件都成立才逐句打字，並在整段錄音中沿用這個決定：「辨識完成後」是「自動插入並複製文字」、這次口述不做 AI 潤稿、找得到錄音開始時的視窗。潤稿要讀整段文字，所以要潤稿的口述維持停錄後一次送出。[逐句打字的狀態](../../app/src-tauri/src/live.rs)

| 情況 | 行為 |
| --- | --- |
| 一句辨識完成 | 這一句各自轉成繁體、整理口語、套用個人詞彙、已學會的改字與取代規則，再轉成使用者選的字體，依全文串接規則接在已打的文字後面，打進目標欄位。標準文字方塊直接寫入；其他程式先複製再送貼上鍵，兩次貼上至少相隔 0.5 秒。 |
| 修飾鍵還按著（按住說話） | 貼上鍵會變成別的快捷鍵，所以不碰剪貼簿也不送鍵。句子留在浮條，等下一句完成或停止錄音時一起送出。標準文字方塊不受影響。 |
| 使用者離開目標視窗或欄位 | 這次錄音不再逐句打字。還沒打進去的文字留在浮條；停止錄音後依既有規則處理，仍不在原處就顯示在預覽並複製，預覽只放還沒打進去的部分。 |
| 程式規則要去掉句尾「。」 | 最後一句的句尾「。」先不打，下一句來時補在前面；停止錄音時就不補。 |
| 某一句失敗、佇列滿或片段不完整 | 停止逐句派送。已打的句子不動；停止錄音後只把最後一句成功句子之後的錄音辨識一次，補在後面。這一段也失敗時，結果仍算完成，訊息加上「最後一段沒有辨識成功」，不提供本機重試，以免重複打字。 |
| 取消 | 已打進去的句子不收回，不記入歷史與改字學習。 |

逐句打字時浮條只保留錄音與音量指示，不列出已打進去的句子。停止錄音後，全部句子都已打完就顯示「已逐句插入文字」，這時不另外改寫剪貼簿；歷史記錄的是全文。

以下各節描述切句、請求與不逐句打字時的流程；逐句打字只改變句子辨識完成後的去處與退回時重辨的範圍。

## 啟用條件

在設定的「語音」頁提供「邊講邊出字」開關，並說明「錄音中會逐句經 Codex 傳到 ChatGPT 辨識」。新安裝與缺少此欄位的舊設定一律預設關閉。只有選用 Codex 時可以操作開關；切換到其他引擎時停用控制項，提示「使用 Codex 時可開啟」。

Rust 在一般口述開始時記下引擎與開關，本次錄音沿用這份設定。開關關閉、使用其他引擎、匯入 WAV 或語音改寫選取文字時，沿用原流程。預設由本機切句，每句都呼叫現有的 `recognise::run(Engine::Codex, …)`，由 `codex-asr` 對一個完整 WAV 做一次辨識。此設計不使用 OpenAI Realtime API 或 Codex 的 WebRTC 內部介面。[辨識路徑](../../app/src-tauri/src/recognise.rs)

## 串流辨識（實驗）

在「語音」頁選擇「Codex 線上辨識」並開啟「邊講邊出字」後，才會顯示「串流辨識（實驗）」。新安裝和缺少此欄位的舊設定都預設關閉。這個聽寫介面沒有官方文件，協定是依 Codex 桌面版的實際行為比對整理，可能隨時改變。

按下錄音或按住說話的快捷鍵時，聽字同時開始麥克風啟動與 TLS／WebSocket 握手。取得裝置取樣率並完成握手後便送出 `session.start`。麥克風錄到的聲音先緩衝，收到 `session.started` 後，連線執行緒每圈依錄音順序送完已累積的完整封包。連線只用於本次錄音。

串流一律將多聲道混成單聲道 PCM16，以裝置原生取樣率傳送，串流辨識時不套用降噪。退回逐句辨識時，剩下的錄音仍依「降噪」設定處理。第一包送 128 個樣本，後續每包 2048 個，收尾時補 250 毫秒靜音。連線後最多等 15 秒確認啟動。送出關閉要求後，等待時間取 15 秒和已送音訊長度兩者中較長者。

伺服器負責斷句。符合逐句打字條件時，聽字把 `transcript.segment` 當作該句目前的完整文字，同一個 `utterance_id` 只採用更高的 `revision`。`transcript.delta` 只計入診斷。中途文字與定稿都沿用逐句的繁簡轉換、口語整理、個人詞彙、改字、取代與句間串接規則。

聽字在原欄位保留兩版相同的開頭，對舊尾端送退格，再用 Unicode 按鍵輸入新尾端，全程不用剪貼簿。獨立的打字執行緒收到中途修訂就轉換文字並更新，轉換後與已打文字相同就略過。若打字跟不上，同一句只保留最新的待處理修訂，定稿則全部依序處理。沒有文字時執行緒會阻塞等待，只有修飾鍵擋住待送按鍵時才定時重試。若一次修訂需要超過 20 個退格，這句等到定稿才改。收到 `transcript.final` 就依句序校正，定稿不受退格上限影響，之後不再修改。未啟用逐句打字時，仍只把定稿交給原流程，同一句採用版號最大的定稿修訂。

按住說話的修飾鍵放開後，聽字才補上最新文字。偵測到焦點離開原視窗或欄位、使用者打字或用按鍵或滑鼠移動游標，就停止送鍵，保留已輸入的內容。取消錄音或串流失敗時，只在目標仍安全時收回未定稿的尾段。退回逐句辨識的音訊從最後定稿的句尾開始。歷史、學習與潤稿只讀取最終全文。每次串流打字記錄中途更新次數、退格總數，以及從錄音開始到送出第一個字的時間。連線記錄包含從啟動錄音到握手完成及收到 `session.started` 的時間、各連線最長的音訊排隊時間（送完封包時，距包內最後一個錄音樣本的估計時間），以及打字執行緒處理一筆中途修訂的最長耗時。這些記錄不含逐字稿、音訊或登入憑證。

聽字無法讀回每種編輯器的欄位內容。編輯器自行移動游標、自動補字，或把多個 Unicode 字元當作一個字素刪除，都可能讓實際退格範圍與計算不同。macOS 還需要系統允許聽字取得焦點資訊、觀察輸入並送出按鍵。這些行為需要在常用的文字欄位實機驗收。

以下兩項是聽字的設計。送滿 240 秒音訊後，在下一次句尾換連線，送滿 285 秒就強制換線。若伺服器送來 `session.stop_requested`，聽字會補靜音、關閉連線並收完定稿。錄音繼續，剩餘音訊改由本機切句，逐句送往 `/transcribe`，這次錄音不再開串流。

遇到連線失敗、握手遭擋、逾時、辨識失敗或致命錯誤，也會退回逐句辨識。未知事件、格式不完整的定稿和非致命通知會略過。關閉時若有句子只有開頭或片段通知，聽字保留從頭連續定稿的句子，從最後一個已交付句子的結尾補辨識。缺句之後即使收到其他定稿，也留給本機切句處理，避免重複打字。句尾優先採用伺服器提供的音訊時間，缺少時間時採用收到通知時已送出的樣本位置，網路延遲可能使接續點偏晚。操作記錄會標示使用串流或退回的原因、句尾到定稿的時間，以及換線次數。

## 本機切句

以下是第一版建議值，待 Windows 與 macOS 實機校準。時間依麥克風原始取樣率換算成單聲道樣本位置，與音量事件的頻率無關。[現有錄音與靜音判定](../../app/src-tauri/src/audio.rs)

| 判定 | 切句器的行為 |
| --- | --- |
| 音量門檻 | 沿用 `sound` 的 20 ms 視窗與公式。現有函式能讀完整段後取最高峰值；錄音中則取最近 1 秒（含當前視窗）的絕對振幅最高值。當前視窗峰值嚴格大於 `max(0.004, 最高值 × 0.08)` 才算有聲。跨回呼接續未滿的視窗，停止時也判讀剩餘樣本，已判讀的視窗不回頭改判。 |
| 自然停頓 | 從第一個有聲窗開始，連續 600 ms 靜音才結句。兩次呼吸間若只停 580 ms，就留在同一句。一句從起點到最後有聲窗已滿 2 秒後，連續 300 ms 靜音就結句；滿 4 秒後，200 ms 就結句，讓連續說話的人不必等到長停頓才看到字。靜音短於句尾保留的 250 ms 時，切點落在靜音結尾。切點在最後有聲窗結尾後 250 ms，下一句從切點以後取樣，句首最多保留 250 ms 靜音。 |
| 最短一句 | 第一到最後有聲窗的跨度至少 200 ms，對應 `too_short` 的判準。若只有短促聲響就遇到足夠長的停頓，先留存其位置，等下一段語音合併。若到停止或長度上限仍無法成句，交完整錄音判斷，避免把短字當成雜音丟掉。純靜音不單獨送件。 |
| 最長一句 | 自片段起點（含句首保留量）算滿 6 秒即強制切。從最後 1 秒的完整視窗中選峰值最低者，在該窗末端切；同值取最晚者。即使全程有聲也用此規則，切點後已讀的樣本歸下一段。相鄰片段使用不重疊的樣本範圍，強切處不另裁音或補靜音。 |

整段用的 `trim` 會盡量保留首尾各 250 ms；若裁後不足 300 ms 則保留原樣。本機切句只借用保留靜音的長度。整段的 `sound`、`trim` 和 `too_short` 仍以同一份原始樣本做最後判斷。

## 錄音、請求與浮條

1. 保留錄音回呼現有的單聲道樣本緩衝區與音量回報。開啟功能時，另由 Rust 工作執行緒按讀取位置分批複製新增樣本，隨即釋放鎖。切句、重取樣、編碼、送件都在鎖外執行。切出一句即送出含錄音識別碼、句序及原始樣本起訖位置的片段通知。待送佇列只存位置，送件前才從完整緩衝區取樣並編成 16 kHz 單聲道 16-bit PCM WAV。
2. 全程保留完整樣本，切句器只移動自己的讀取位置。停止時先關閉輸入，固定最後樣本位置，讓切句器讀到該處後才關閉片段通知。錄音上限為十分鐘，過短的輸入仍回傳相同錯誤。完整 WAV 與逐句辨識共用開始錄音時的「降噪」設定。開啟時在自動增益前處理音訊，切句與裁切仍使用原始樣本。詳見[辨識前的音訊處理](app-migration.md#辨識前的音訊處理)。
3. Rust 按句序派送，同時最多 1 個 Codex 辨識請求，另容許 3 句排隊。頻繁停頓會增加請求數，服務可能回傳 HTTP 429。佇列滿時若又切出一句、收到 429、任一句出錯或逾時，都停止逐句派送，改走下節的整段流程。沿用現有 Codex 用戶端的 90 秒請求逾時，不自動重送單句，也不假設帳號有固定配額。
4. Rust 持有本次錄音的句序、已定稿句子及待辨識數量，發送帶錄音識別碼與遞增版本的完整浮條狀態。浮條保留錄音與音量指示，依序逐行顯示定稿句；有句子排隊或送出時，另起一行顯示「辨識中…」。例如第一句回來、第二句仍在等候時，第一行是「明天開會。」，末行是「辨識中…」。回應到達後以定稿句取代狀態行；若還有待辨識句，再顯示狀態行。文字過長時讓最新一句可見，維持原本輸入焦點。
5. UI 只呈現 Rust 提供的狀態，忽略過期畫面事件。預覽文字與可貼上的最終全文分開存放。不逐句打字時，顯示中途文字不碰剪貼簿與貼入目標；兩種方式都要到停止錄音後才寫入歷史與學習資料。停止錄音後仍沿用同一次錄音識別碼收齊結果，不能因進入辨識階段而把尾句誤當成上一輪回應。

## 放開快捷鍵後如何定稿

放開按住說話的快捷鍵、切換式錄音再次按鍵停止，或達到十分鐘上限時，都走同一條收尾流程。依既有快捷鍵規則，短按鎖定錄音時，放開不算停止。收尾時即使末句沒有 600 ms 停頓，也送出最後一段達 200 ms 的語音。只有靜音的尾巴不增加句數。若有尚未送出的短音、全程沒有成句，使用完整錄音辨識。有聲片段只得到空白文字時（例如咳嗽或換氣），略過這一句，不算失敗；但全部句子都是空白時，仍使用完整錄音辨識。若 `finish()` 已判定整段太短或錄音失敗，直接顯示原錯誤。

| 全文來源 | 使用者會觀察到的取捨 |
| --- | --- |
| 依序串接逐句結果（建議） | 全部句子成功時，只需等尚未完成的句子。全文保留浮條上已看過的用字，省下一次完整上傳。人名、標點或在強切點拆開的詞可能因少了上下文而辨識不準。 |
| 每次都把完整 WAV 重辨一次 | 辨識器可參考前後句，也能重新判讀被切開的詞。每次停止都要重新上傳並等待，且最終文字可能與浮條預覽不同。 |

建議以串接為正常路徑。Rust 確認從首句到尾句都有唯一的結果（空白的句子略過），依序去除各句首尾空白，保留原有標點。中文直接相接；若邊界兩側都是 ASCII 英數字元，補一個空格。不依停頓自動加句號，也不刪除使用者重複說的詞。

有任何缺句或前述失敗時，清除逐句預覽，錄音中顯示「停止錄音後會辨識還沒出字的部分」。錄音照常繼續。停止後顯示「整段辨識中」，使用 `finish()` 的完整 WAV 走原本 Codex 整段辨識一次。只採用這次的完整結果，避免已回來的句子重複貼入。整段也失敗時顯示既有錯誤，沿用本機引擎可用時保留錄音供重試的行為。即使服務持續限流，也不能以半份文字當作成功。

取得唯一的全文後才交給 Rust 現有的收尾流程。先轉成繁體，依設定整理口語、進行 AI 潤稿，再套用個人詞彙、已學會的改字與取代規則。最後轉成使用者選擇的簡繁字體，套用目標程式的文字規則，依既有模式一次貼入、複製或預覽。開啟歷史時才記錄這次全文；實際貼入且啟用改字學習時，才以最終全文追蹤後續修正。[口述收尾與學習條件](../../app/src-tauri/src/main.rs)

取消與停止送出是兩個操作。取消錄音、等待辨識或整段重辨時，Rust 立即使本次錄音識別碼失效，關閉切句器、清空待送片段並收回預覽。取消後不啟動整段重辨。現有 Codex 呼叫會阻塞，已送出的音訊無法收回；在請求返回或逾時前仍占用請求名額，晚到的結果一律丟棄。取消後可以開始新錄音；舊回應不得更新新浮條、貼字或留下學習紀錄。

## 建議的 PR 切分與驗收

**PR1　錄音片段、中途事件、浮條與開關。** 先完成本機切句、設定相容與 Rust 狀態事件。用測試替身送出延遲的句子驗證浮條。正式使用時仍走原本的整段辨識，開關標明準備中並保持停用，直到 PR2 接上服務。

**PR2　接上 Codex 逐句辨識。** 啟用 Codex 專用開關，接上逐句請求、佇列、取消、尾句、全文串接與整段退回。兩個 PR 都需要在 Windows 與 macOS 上跑 `cargo test --locked`。以下是要新增的測試，實作時才執行。

| 階段 | cargo test 案例與預期 |
| --- | --- |
| PR1 切句 | 用合成樣本涵蓋等於與略高於振幅門檻、580 與 600 ms 停頓、180 與 200 ms 有聲、長靜音、先大聲後小聲。改變回呼分塊大小與原取樣率，切點仍對應同一音訊時間。 |
| PR1 完整錄音 | 驗證 6 秒強切位置、同值取最晚、切點後樣本歸屬、尾端不足一窗與十分鐘邊界。比較有無切句時完整 WAV 的每個位元組及過短錯誤。 |
| PR1 設定與事件 | 舊設定缺欄位預設關閉，非 Codex 不產生片段。測試替身依序傳回兩句，確認「辨識中…」出現與消失，重複或過期事件不改畫面；停止前送出、歷史、學習的呼叫次數都是零。 |
| PR2 正常收尾 | 模擬有聲尾句、純靜音尾巴、整段無聲及過短尾音。成功時核對中文、英數、重複詞與跨句取代的全文；潤稿只收到一次全文，貼入與符合條件的學習各一次。 |
| PR2 退回與取消 | 用替身依次模擬中間一句失敗、逾時、429、佇列滿；中間或尾句空白時略過該句、不退回。檢查同時最多一個請求，整段退回只收一次原完整 WAV，整段也失敗時貼入零次。分別在錄音、排隊、等待尾句及整段重辨時取消，再開始新錄音，驗證晚到回應無副作用。 |

**只能實機驗收的項目**

- 在 Windows 與 macOS 用實際麥克風說短字、輕聲、連續長句，加入換氣、背景音與長停頓。聽辨強切處的人名與句尾，記下停頓到浮條出字、放鍵到全文送出的時間，據此調整門檻。
- 使用已登入 Codex 的帳號驗證真實上傳與回應，測試慢速網路與斷線。若遇真實 429，確認停止逐句送件並顯示退回狀態；固定重現 429 的驗收用測試替身。
- 在實際文字編輯器與聊天輸入框按住說話，確認浮條更新時焦點仍在原處，放鍵後全文只出現一次。再測切換式停止、取消後立刻重錄，以及預覽模式。macOS 要另外確認麥克風與貼入所需權限。
